The application process

What happens between a renter pressing Apply and an owner saying yes — the conversation it opens, the facts it carries, the facts it must refuse to carry, and the failure each decision was tested against.

Status: proposal Audience: product, backend, renter & owner front-ends Companion: docs/onboarding-handoff.html
Part zero

Where we are today

Six findings from reading the code rather than the roadmap. The first one decides how much of the rest is a change and how much is a build.

The audit

Finding 1 — the most important one

The renter app never submits an application. In apply-view.tsx the handler is const send = () => setSent(true). It flips a local boolean and renders the success screen. Nothing reaches the server. The same is true of the mobile path in listing-detail.tsx.

So every renter who has "applied" on Ampl has applied to nothing, and every owner who has seen an empty applications list was reading the truth. This is not a bug to patch at the end — it means the flow below is being built, not repaired, and we get to choose the shape rather than inherit it.

What already works and should be kept

The messaging system is complete and good: conversations, participants, messages, attachments with presigned two-phase upload, unread high-water marks, and a send_message that already dispatches notifications and email. The application flow should use it, not grow a parallel inbox.

Part one

The reference, and where we leave it

Airbnb's request-to-book is the closest working model and worth copying in shape. It is also solving a materially different problem, and four of those differences change the design rather than decorate it.

Same shape

  • A request carries dates, a short message, and an identity that has already been verified.
  • Sending it opens a thread automatically. The thread is the record of the negotiation.
  • The host sees a structured summary at the top of that thread, not a wall of profile fields.
  • The exact address is released on acceptance, never before.
  • Requests expire. An unanswered one does not sit forever pretending to be live.

Four differences that change the design

01 · It is a selection, not a sale

A host with a free night accepts the first acceptable guest. An owner with one unit is choosing between applicants, often over days. So our statuses need a real waitlisted, approving one applicant has to do something to the others, and "pending" has to distinguish unseen from under consideration.

02 · No money changes hands

Airbnb pre-authorises a card, which filters out unserious requests for free. We have no such filter, so spam control has to be explicit: rate limits, a cooldown after a decline, and a cap on open applications.

03 · Documents are the substance

Nobody sends a payslip to book a weekend. A tenancy turns on income, references and sometimes a guarantor. That makes document exchange a first-class part of the flow — and makes consent per document a requirement rather than a nicety.

04 · Housing is a protected transaction

Choosing a guest for two nights and choosing who gets a home are not the same act in law. Ontario's Human Rights Code governs the second. Fields that are harmless on a travel profile become a discrimination surface on a tenancy application — see Part 4.

Part two

The process

One submission, one application record, one conversation, one structured card inside it. Everything else is a transition on that record.

The happy path, step by step

01
Renter · listing page

Presses Apply

Signed out, this opens auth first — an application with nobody's name on it is not an application. Signed in with an incomplete profile, the missing fields are asked here, inline, rather than bouncing them to a profile page. The funnel dies at every redirect.

02
Renter · apply sheet

Confirms three things and writes one

Move-in date, lease length, and who is moving in. Then a free-text note to the owner. Nothing else: every additional field on this screen is a percentage of applications that never get sent.

03
Server · one transaction

Creates the application, the thread, and the first message

Application row at submitted; a conversation scoped to this renter, this owner, this property; an application card pinned to it; and the renter's note posted as the first message from the renter. All four commit together or none of them do — an application with no thread is a dead end, and a thread with no application is a mystery.

04
Owner · notification + email

Is told, and can reply without deciding

The notification links to the thread, not to a decision screen. The owner's first action is usually a question, and today the product forces them to approve before they can ask it.

05
Owner · thread

Opens it — which the renter can see

viewed_at is stamped. The renter's status moves from "Sent" to "Being reviewed". This is the single most requested thing in every rental product and we currently guess at it client-side.

06
Owner · thread

May request documents

From a short allowed list. The renter grants or refuses per document; a refusal is visible as a refusal rather than as silence. Documents are attached to the application, not pasted into chat, so access can be withdrawn.

07
Owner · decision

Approves, waitlists, or declines

On approval: the exact address unlocks for that renter, the lease flow opens, and every other submitted application on that property is nudged — see scenario 8.

pending disappears as a stored value. It currently means two things the renter reads very differently — "sent and unopened" and "read and being decided" — which is exactly why the renter app invents a not-reviewed status of its own. One honest field replaces one client-side guess.

Part three

The conversation

Applying opens a thread. What that thread contains is the decision with the longest tail, because a message cannot be unsent and a chat log is trivially forwarded.

One thread per application, not per pair

Conversation.dm_key is unique on the sorted pair of user ids, so today one renter and one owner can only ever have one thread. An owner with twelve properties and a renter who applies to three would get one conversation carrying three negotiations, and every message would begin with working out which home it is about.

The fix is to widen the key rather than remove it: dm_key becomes "<renter>:<owner>:<onboarding>" for application threads, and the conversation carries a nullable onboarding_id. Plain DMs keep the two-part key and the same uniqueness guarantee they have now.

A card, not a paragraph

The tempting version, and why not

The obvious implementation is to post the renter's details as the opening message: "Priya Nair, 24, from India, student at UofT, budget $2,000…". It is one insert and it renders everywhere for free.

It is also permanent, forwardable, and immediately stale. If the renter withdraws, the message stays. If they correct their move-in date, the message still shows the old one. And it hard-codes personal data into a log that no later privacy decision can reach.

So the thread carries a reference — a pinned card rendered live from the Application row at read time. It updates when the application does, disappears when the application is withdrawn, and honours whatever the field-level rules in Part 4 say on the day it is read rather than the day it was written.

The renter's own note is a real message, posted as them. They wrote it, they meant to send it, and it should sit in the thread like anything else they type.

Part four

What the owner may see

The one part of this spec that is not a product preference.

The exposure we would be building

TenantProfile holds date_of_birth, gender, nationality, country_of_origin and is_international. Ontario's Human Rights Code prohibits refusing housing on grounds including place of origin, citizenship, ethnic origin, creed, sex, gender identity, age, marital status, family status and receipt of public assistance.

Auto-sending those fields to an owner at the moment they decide would not merely risk discrimination — it would manufacture the means, and leave Ampl's own timestamped record that we supplied it. The conservative default is that the application card carries none of them, and that is the default this spec takes.

FieldOn the cardReasoning
Name, photoYesThey are about to let this person into their home
Move-in date, lease lengthYesThe terms being asked for
Who is moving in (count)YesOccupancy is a legitimate property question
Tenant type (student / professional)YesAlready public on the profile and shapes the conversation

Income verified badgeYesA boolean, not a number — see the note below

Employment letter, references, guarantorOn requestPer-document consent, revocable

Gender, pronounsNoProtected ground, and irrelevant to tenancy

Not legal advice

This table is a conservative engineering default written from the public shape of the Human Rights Code and O. Reg. 290/98, not from counsel. Before launch it needs a lawyer's eye — particularly the income row, where the regulation permits more than this table allows and the safer default may be costing owners a legitimate signal.

The match percentage

It is currently 85 for everybody, written into the insert. Owners are being invited to rank humans by a constant. Three options, in order of preference:

  1. Remove it until there is something to compute. Nothing is lost that was ever real.
  2. Compute it from facts we hold — budget against rent, move-in against availability, occupancy against bedrooms, preferences against amenities — and show the inputs when it is tapped, the way Atlas shows its pillars.
  3. Keep a constant and label it as a placeholder. Not recommended: a number labelled provisional is still a number people sort by.
Part five

The pressure test

Twelve ways the flow above gets abused, confused or deadlocked, and what it does about each. Every one of these is a decision somebody will otherwise make by accident during implementation.

1. A renter applies to forty homes in five minutes breaks today
Nothing stops them. Forty owners get a notification from someone who has looked at nothing.
Do: cap open applications per renter (suggest 10) and rate-limit submissions (suggest 5/hour). The cap is the better lever — it makes the renter close one before opening another, which is also the honest behaviour.
2. Owner declines; renter re-applies immediately, repeatedly breaks today
The current guard only blocks re-applying while the previous application is not declined — so a decline is precisely what unlocks the retry.
Do: a cooldown after a decline (suggest 30 days) and a hard limit of two applications per renter per property, ever. Re-applying after a decline should require the owner to invite it.
3. Owner approves two renters for one unit
Both see "approved", both see the address, both start a lease flow. One of them is going to be told later that it was a mistake.
Do: approving is allowed while the property is listed, but the second approval warns explicitly ("Maya is already approved for this home"). On the first approval, every other submitted/viewed application is auto-moved to waitlisted with a message — never to declined, which is the owner's word to say, not ours.
4. Owner never responds breaks today
The application stays pending forever. This is the single loudest complaint in every rental marketplace.
Do: expire at 14 days with no viewed_at, 30 days with no decision. The renter is told, the slot returns to their cap, and the owner's listing accrues a visible "usually replies in…" that the next renter can read.
5. The renter changes their mind breaks today
There is no withdraw. Their only options are to ghost the owner or ask them to decline it.
Do: withdrawn, from the applications list and the thread. The thread stays — a conversation both people participated in is not ours to delete — but the card collapses to "Withdrawn on 4 Oct".
6. The property is unlisted or rented while applications are open
Applications point at an Onboarding that is no longer in LISTED_STATES. The renter's list still shows them as live.
Do: unlisting expires every open application on that property with a distinct reason ("No longer available"), which reads very differently to a renter than silence does.
7. Two renters apply from one account, or one renter applies twice for a shared flat
Occupancy is asked as a count today and nothing links co-applicants.
Do: out of scope for v1, and say so. A group application is a real feature with its own consent model; approximating it with a number field is how you end up with a lease naming the wrong people. v1 asks "how many people" and lets the owner ask the rest in the thread.
8. Owner asks for a SIN, a bank login, or a photo of a passport in chat
Nothing prevents it, and the renter has no signal that the request is improper.
Do: document requests go through a typed control with an allowed list, and free-text chat carries a quiet, non-blocking hint when it detects those terms. Not a block — an owner asking a reasonable-sounding question should not hit a wall — but the renter should know they are allowed to say no.
9. Renter applies with an empty profile breaks today
The endpoint 400s with "Complete your student profile before applying", and the renter app has no screen that resolves it.
Do: create the TenantProfile lazily at first apply, and gate on a minimum — verified email and a name — rather than on completeness. Ask for the rest inline in the sheet. Profile completeness becomes a badge on the card, not a barrier at the door.
10. The thread exists but the application is gone
Withdrawn or expired applications leave a conversation whose header refers to a record that no longer explains itself.
Do: the card renders the terminal state rather than vanishing. A thread whose context disappears is worse than one that says why it ended.
11. Owner and renter are the same person, or the owner applies to a peer's listing
Self-application is already blocked. Owner-as-renter is not, and should not be — an owner is allowed to rent somewhere.
Do: keep the self-check, allow the cross-role case, and make sure the thread's participant roles are derived from the application rather than from the account's type. Someone can be an owner in one thread and a renter in the next.
12. Notification succeeds, message fails — or the reverse
Today the approval path wraps send_message in a bare except and continues, so an approval can silently produce no message.
Do: for apply, the application, conversation, card and first message are one transaction — a half-created application is not recoverable by the renter and they will simply apply again. Notifications and email stay best-effort and outside it, because a failed email must never lose an application.

The one job

Expiry needs a scheduled task. Celery is already configured and running a worker, so this is a beat task rather than new infrastructure: sweep for viewed_at IS NULL past 14 days and undecided past 30, move them to expired, notify both sides.

Part seven

Open decisions

Six things this spec has taken a position on that are genuinely yours to settle.

  1. The match percentage. Remove, or compute? Removing ships this week; computing is a real piece of work and needs its own honesty rules.
  2. Expiry windows. 14 days unopened / 30 days undecided are placeholders chosen to feel fair. Real numbers should come from what owners actually do once there is data.
  3. The open-application cap. 10 is a guess. Too low and serious renters hit it in a weekend; too high and it stops being a filter.
  4. Income on the card. Part 4 defaults to a badge, not a figure. Ontario permits more. This is the row most likely to be wrong in the cautious direction.
  5. Group applications. Deferred to v2 here. If shared housing is a launch segment rather than a later one, that changes the data model now rather than later.
  6. Does a decline release the address? No, in this spec. Worth confirming — a renter who visited the property already knows it, and pretending otherwise is theatre.
The smallest version that is honest

If only one thing ships: make Apply actually submit, open the thread with the renter's note in it, add viewed_at and withdrawn, and delete the hardcoded match score. That is a working, truthful application flow. Everything else in this document makes it safer and fairer, but that is the part where the product starts existing.
